# PIC16 Firmware Analysis

The iDCM board's PIC16LF15355 (U10) bridges the MW300 WiFi module and the main
board's motor controller. This document describes the firmware's structure.

## Role in the System

```
MW300 (Sesame firmware)          PIC16 (U10)              Main board PIC
        │                           │                           │
        │──── UART1 (115200) ──────►│                           │
        │◄─── UART1 (115200) ───────│                           │
        │                           │──── UART2 ───────────────►│
        │                           │◄─── UART2 ────────────────│
```

The PIC acts as a gateway: door commands from the MW300 are forwarded
transparently to the main board; audio and alert commands are executed locally
(buzzer on the iDCM board); door status flows back from the main board to
the MW300.

Note: the two status LEDs on the iDCM board are driven directly by the MW300's
own GPIOs (see `src/leds.c`), not by the PIC.

## Hardware Configuration

| MCLR       | External (pulled high by 10 kΩ to VDD)        |

## GPIO Outputs

The PIC drives several output pins whose exact board-level connections are not
fully known without a schematic. The following is derived from disassembly:

| Pin | Likely function          | Evidence                                                                                |
| --- | ------------------------ | --------------------------------------------------------------------------------------- |
| RA5 | Buzzer drive/enable      | Set/cleared inside the audio command processor (`function_031`) in sync with tone value |
| RA1 | Light or door-status signal to main board | Set when a door command is processed (countdown stored); cleared when countdown reaches zero — timed-on/off behaviour after door movement |
| RA7 | Unknown                  | Manipulated in `label_221` (0x1A handler) and LED pattern code; no clear functional correlation |

## Serial Protocol

Frames are identical in both directions on UART1. The MW300 side documents
the format in `include/idcm_msg.h`.

```
┌────────┬────────┬────────┬────────┬─ payload ──┬──────────┐
│ 0x55   │  len   │  seq   │  type  │  len bytes │ checksum │
│ 1 byte │ 1 byte │ 1 byte │ 1 byte │            │  1 byte  │
└────────┴────────┴────────┴────────┴────────────┴──────────┘
```

- **Checksum**: CRC-8 across all bytes from header through payload (`bytes[:len+3]`).
- **Sequence number**: generated by the MW300 (`next_token()` in
  `pic_uart.c`); certain values (77, 85) are skipped, range is 1–252.
- **Maximum payload**: 35 bytes (`MAX_DCM_MSG_SIZE - 1`).

## Interrupt Service Routine

The ISR at 0x0400 polls each interrupt flag in priority order:

| Priority | Flag   | Handler        | Purpose                             |
| -------- | ------ | -------------- | ----------------------------------- |
| 1        | CLC2IF | `function_030` | Configurable Logic Cell 2           |
| 2        | CLC1IF | `function_087` | Configurable Logic Cell 1           |
| 3        | IOCIF  | `function_141` | GPIO interrupt-on-change (RB0, RB1) |
| 4        | TMR1IF | `function_145` | Timer1 — timing/LED/alert pulse     |
| 5        | RC1IF  | `function_082` | **UART1 RX** from MW300             |
| 6        | RC2IF  | `function_143` | UART2 RX from main board            |
| 7        | TX1IF  | `function_080` | **UART1 TX** to MW300               |
| 8        | TX2IF  | `function_144` | UART2 TX to main board              |

## UART Buffering

### UART1 RX (`function_082`)

Circular buffer, 128 bytes, base address 0x2248 (linear). Write index in
register bank-1 offset 0x65. Byte count in 0x05D. Overrun (OERR) is
recovered by toggling CREN.

### UART1 TX (`function_080`)

Circular buffer, 128 bytes, base 0x22C8. Read index in bank-1 offset 0x66.
Pending-byte count in 0x16E. TX1IE is cleared when the buffer empties.

### UART2 RX (`function_143`)

Linear buffer, 32 bytes, base 0x0220. Byte count in register 0x5C.

### UART2 TX (`function_144`)

Linear buffer, 32 bytes, base 0x01A0.

## Main Loop

```
function_114 (main loop, ~50 ms cycle):
  ├── function_115   kick watchdog (CLRWDT)
  ├── function_120   drain UART2 RX queue (main board messages)
  ├── function_062   assemble and validate UART1 frames
  ├── function_121   process MW300 responses
  └── function_000   dispatch MW300 commands (calls function_146)
```

The loop waits until a polling counter reaches 50 before iterating, giving
approximately 50 ms per cycle.

## Message Dispatch (`function_146`)

Handles messages **received from the MW300** on UART1. The type byte is
compared via a chained XOR sequence:

| Type    | Constant                      | Handler label             | Action                                          |
| ------- | ----------------------------- | ------------------------- | ----------------------------------------------- |
| 0x10    | `DCM_MSG_DOOR_CMD`            | `label_273`               | Forward frame to main board via UART2           |
| 0x11    | `DCM_MSG_ALERT_CMD`           | `label_275` → `label_284` | Execute alert locally; reply 0x91 (`ALERT_ACK`) to MW300 |
| 0x12    | `DCM_MSG_AUDIO_CMD`           | `label_276` → `label_281` | Drive buzzer; reply 0x92 (`AUDIO_ACK`) to MW300 |
| 0x13    | _(undocumented)_              | `label_280`               | Silently ignored                                |
| 0x15    | `DCM_MSG_DOOR_STATUS_REQUEST` | `label_271` → `label_286` | Reply with current door state (0x16)            |
| 0x18    | `DCM_MSG_FACTORY_TEST`        | `label_277` → `label_285` | Factory test handler                            |
| 0x1A    | _(undocumented)_              | `label_279`               | Unknown                                         |
| 0x1B    | _(undocumented)_              | `label_272`               | Unknown                                         |
| 0x94    | _(undocumented)_              | `label_278`               | Token validation; clears pending-response flag  |
| _other_ | —                             | `label_280`               | Silently ignored                                |

The three undocumented types (0x13, 0x1A, 0x1B) are absent from
`idcm_msg.h`; they may relate to LED control, PIC firmware update, or
diagnostics present in the original Aladdin Connect protocol.

### Door Command Pass-Through (0x10)

`function_067` copies the raw frame from the UART1 receive buffer directly
into the UART2 transmit buffer. The PIC does not interpret the door command
payload; the main board's PIC executes the motor action.

### Door Command Pass-Through Response (0x90)

After forwarding a `DCM_MSG_DOOR_CMD` to the main board, the PIC replies to
the MW300 with `DCM_MSG_DOOR_RESPONSE` (0x90), echoing the same sequence
number. Confirmed in logs: every 0x90 frame shares its seq byte with the
preceding 0x10 DOOR_CMD.

### Audio / Alert Commands (0x11, 0x12)

Executed locally on the iDCM board (buzzer, visual alert LEDs). A response
frame is constructed by `function_066` and queued for UART1 TX back to the
MW300. Response types are 0x91 (`DCM_MSG_ALERT_ACK`) for alerts (`label_284`
writes `0x91` into the type field) and 0x92 (`DCM_MSG_AUDIO_ACK`) for audio.

### Door Status Request (0x15)

The PIC assembles a `DCM_MSG_DOOR_STATUS_UPDATE` (0x16) response containing
the current position, travel limits, open/closed state, and direction, then
sends it back to the MW300 on UART1.

### Response Correlation (0x94)

The PIC tracks one outstanding request token in register 0x061. On receiving
type 0x94, it compares the frame's sequence number against the saved token; a
match clears the pending-response flag (register 0x158), completing the
request-response handshake.

## Frame Assembly (`function_066`)

Outgoing frames to the MW300 are built in a staging buffer at 0x2348:

1. Write header `0x55` at offset 0.
2. Write length at offset 1 (from register 0x0AF).
3. Write sequence number at offset 2.
4. Write message type at offset 3.
5. Copy payload from source pointer (registers 0x0AD/0x0AE) to offsets 4+.
6. Compute XOR checksum over bytes 1 … len+3 (`function_078`).
7. Enqueue in UART1 TX circular buffer (`function_079`/`function_068`).

## Known Message Types (MW300 → PIC)

These are the types the MW300 sends and the PIC accepts:

| Type | Name                          | Payload                              | Notes                                                     |
| ---- | ----------------------------- | ------------------------------------ | --------------------------------------------------------- |
| 0x04 | `DCM_MSG_0x04`                | 9 bytes (zeroed)                     | Sent every 30 s alongside status request; purpose unknown |
| 0x10 | `DCM_MSG_DOOR_CMD`            | `{val, 0}` — val=1 open, val=0 close | Forwarded to main board                                   |
| 0x11 | `DCM_MSG_ALERT_CMD`           | `{val, 5, 0}`                        | Visual alert; val=1 activate                              |
| 0x12 | `DCM_MSG_AUDIO_CMD`           | `{val, unk1, 0}`                     | Buzzer; val=1 beep, val=2 alert tone, val=5 self-test     |
| 0x15 | `DCM_MSG_DOOR_STATUS_REQUEST` | 12 bytes incl. pos, limits           | Triggers 0x16 response                                    |

## Known Message Types (PIC → MW300)

| Type | Name                         | Payload  | Notes                                                             |
| ---- | ---------------------------- | -------- | ----------------------------------------------------------------- |
| 0x14 | `DCM_MSG_STATUS_UPDATE`      | 14 bytes | Factory test mode status report                                   |
| 0x16 | `DCM_MSG_STATUS_UPDATE_EXT`  | 28 bytes | Periodic door status report (time, reserved, state, dir, pos, up_limit, motor_current, down_limit, extra) |
| 0x17 | `DCM_MSG_OPS_EVENT`          | 10 bytes | event code, limits; logged but not acted on by MW300              |
| 0x90 | `DCM_MSG_DOOR_RESPONSE`      | 2 bytes  | ACK for door command; seq echoes the DOOR_CMD                     |
| 0x91 | `DCM_MSG_ALERT_ACK`          | —        | ACK for alert command                                             |
| 0x92 | `DCM_MSG_AUDIO_ACK`          | —        | ACK for audio command; MW300 uses receipt to set `self_test_done` |
| 0x95 | `DCM_MSG_SENSOR_VERSION`     | 21 bytes | PIC fw version, caps, and initial door state sent at boot         |

### Extended Door Status Wire Layout (0x16)

The 28-byte payload of `DCM_MSG_STATUS_UPDATE_EXT` (0x16) is structured as follows:

| Offset | Size | Field           | Description                                       |
| ------ | ---- | --------------- | ------------------------------------------------- |
| 0–3    | 4B   | `time`          | Uptime / timestamp counter (uint32)               |
| 4–5    | 2B   | `reserved`      | Always 0x0000 in wire frames (uint16)             |
| 6      | 1B   | `state`         | `door_open_state_t` (0=CLOSED, 1=OPEN, etc.)      |
| 7      | 1B   | `direction`     | `door_direction_t` (0=STOPPED, 1=UP, 2=DOWN)     |
| 8–9    | 2B   | `pos`           | Raw optical encoder count (uint16)                |
| 10–11  | 2B   | `up_limit`      | Calibrated open travel limit (uint16)             |
| 12–13  | 2B   | `motor_current` | Motor load reading (0xFFFF in status frames)      |
| 14–15  | 2B   | `down_limit`    | Calibrated closed travel limit (uint16)           |
| 16–27  | 12B  | `extra`         | Trailing status flags and zero padding            |

## Door State Encoding

| Field        | Type                | Values                             |
| ------------ | ------------------- | ---------------------------------- |
| `state`      | `door_open_state_t` | 0=CLOSED, 1=OPEN, 2=UNKNOWN, 4=FTM |
| `direction`  | `door_direction_t`  | 0=DOWN, 1=UP, 2=STOPPED, 3=UNKNOWN |
| `pos`        | uint16_t            | Raw encoder count                  |
| `up_limit`   | uint16_t            | Encoder count at fully open        |
| `down_limit` | uint16_t            | Encoder count at fully closed      |

The MW300 converts raw position to a 0–100 percentage:
`pos% = 100 × (raw_pos − down_limit) / (up_limit − down_limit)`.
